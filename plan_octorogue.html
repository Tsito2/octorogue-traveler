Octorogue Traveler → Roguelite tactique

Feuille de route pour faire évoluer le prototype actuel (menu → combat de démonstration) vers la vision cible : boucle roguelike, gestion d'équipe jusqu'à 8 personnages, Break/Boost/Pouvoir Latent/Duo Swap. Priorité absolue donnée aux structures Personnages / Classes / Compétences ; les boss sont traités en dernier.

Jeu 100% hors-ligne, JSON local Aucun code TypeScript modifié par ce plan Livrable unique : plan_octorogue.html

01Résumé de l'analyse de l'existant

Le dépôt contient déjà un moteur de combat fonctionnel et data-driven — une base réutilisable solide pour la vision roguelite — mais il coexiste avec un module de code mort qu'il faut trancher avant d'empiler de nouvelles mécaniques dessus.

✅ Réutilisable tel quel
  • src/core/stats.ts — modèle BattleStats/Stats/Resources, bonne base d'extension pour rangée et Pouvoir Latent.
  • src/core/skills.ts, jobs.ts, enemies.ts — types de données déjà pensés en dictionnaires indexés par id, extensibles sans casser l'existant.
  • src/core/formulas.ts — calcul de dégâts, précision/esquive, critique, Break déjà implémentés et isolés en fonctions pures : point d'ancrage naturel pour Boost, Break variable et Pouvoir Latent.
  • src/core/combat.ts (CombatEngine) — orchestrateur de tour déjà structuré autour d'un type Action extensible.
  • src/data/*.json + wrappers .ts — pipeline JSON → dictionnaire typé déjà en place et réutilisé à l'identique sur 4 fichiers : c'est exactement le pattern à répliquer pour les nouvelles données (routes, formations, nœuds de run).
⚠️ À nettoyer avant d'étendre
  • src/characters/Character.ts, Hikari.ts et src/combat/*.ts (hors scènes) + src/ui/HUD.ts/DialogueBox.ts : module orphelin, importé par aucun fichier actif. Duplique le moteur de combat avec une API divergente (classes Character/Party/BattleManager vs le système actuel BattleStats/CombatEngine).
  • README.md racine obsolète (arborescence décrite ne correspond plus au dépôt réel).
  • config.yaml à la racine : workflow CI mal placé (devrait être dans .github/workflows/), inopérant en l'état.
  • Le champ ip/maxIP existe déjà dans Resources mais n'est ni affiché ni consommé : c'est la base technique du futur Pouvoir Latent, à renommer/finaliser plutôt qu'à recréer.
  • L'action "defend" est codée en dur dans CombatEngine.resolveAction plutôt que définie comme compétence de donnée — pattern à éviter pour les futures mécaniques (Burst, Duo Combo) qui doivent rester pilotées par JSON.
Décision structurante : ne pas construire les nouvelles mécaniques (Duo Swap, Burst) par-dessus le module orphelin. Toute nouvelle logique de combat doit s'appuyer exclusivement sur core/combat.ts + core/formulas.ts + core/stats.ts, qui sont le seul moteur réellement exécuté par le jeu.

03Roadmap technique

Quatre phases séquentielles. La Phase 1 (Personnages / Classes / Compétences) est le socle non négociable de tout le reste, conformément à la priorité donnée par le projet. Les boss (Phase 4) sont volontairement traités en dernier.

Phase 0 — Nettoyage & fondations saines🔴 Critique
Objectif : partir d'une base de code à moteur unique avant d'ajouter la moindre mécanique.
  • Exécuter les actions immédiates de la section 02.
  • Geler l'interface publique de CombatEngine/formulas.ts comme unique point d'extension pour toutes les mécaniques à venir.
Fichiers concernés : src/characters/*, src/combat/* (hors scènes), src/ui/*, README.md, config.yaml, src/core/stats.ts
Phase 1 — Fondations Personnages / Classes / Compétences🔴 Critique — priorité absolue du projet
Objectif : porter les structures de données au niveau requis par la vision cible avant tout travail sur la boucle roguelite ou les boss.
  • Étendre l'interface Skill : breakPower, lpGain, isBurst, requiredRow, isDuoCombo (détail schéma en section 04).
  • Étendre l'interface Job : burstSkillId, preferredRow, maxBP (actuellement codé en dur à 5 dans core/encounters.ts — à faire porter par le job).
  • Étendre CharacterTemplate : startingRow, duoAffinity, recruitRouteId, subJob (optionnel, réservé post-MVP).
  • Étoffer le contenu de donnée : passer de 2 à un roster cible de 8 personnages jouables, d'au moins 4 à 6 jobs (contre 2 actuellement), et d'une bibliothèque de compétences couvrant chaque job avec au moins une compétence de soin/buff réelle (le type "support" existe déjà dans SkillCategory mais 0 compétence l'utilise aujourd'hui) et une compétence Burst par job.
  • Ajouter le traitement effectif des cibles "single_ally" et "self" dans le moteur, actuellement définies dans le type SkillTarget mais jamais gérées par CombatEngine — prérequis pour toute compétence de soin/buff.
Fichiers concernés : src/core/skills.ts, src/core/jobs.ts, src/data/characters.ts, src/data/*.json, src/core/encounters.ts
Phase 2 — Calculateurs de combat : Break, Boost, Pouvoir Latent, Duo Swap🟠 Haute
Objectif : faire vivre dans le moteur les structures posées en Phase 1.
  • Break : dans formulas.ts::applyBreak, remplacer le décrément fixe de bouclier (-1) par skill.breakPower ?? 1.
  • Boost (BP) : exposer réellement bpSpent dans CombatScene (actuellement toujours 0 dans tous les appels) via un contrôle +/- avant validation d'une compétence ; utiliser job.maxBP issu de la Phase 1 au lieu de la constante codée en dur.
  • Pouvoir Latent (Burst) : finaliser gainLP (basé sur skill.lpGain, avec repli sur les constantes actuelles IP_ON_DAMAGE/IP_ON_BREAK renommées), ajouter canBurst(actor) (lp >= maxLP) et une résolution resolveBurst qui consomme toute la jauge et exécute la compétence job.burstSkillId avec un multiplicateur dédié.
  • Duo Swap : ajouter row: "front" | "back" et duoPartnerId?: string à BattleStats ; ajouter un type d'action "swap" dans CombatEngine pour échanger la rangée d'un binôme ; ajouter un type d'action "duoCombo" qui déclenche une compétence marquée isDuoCombo lorsque les deux membres du binôme sont vivants et en rangée avant.
Point de conception ouvert (à valider avant implémentation) : le Duo Combo doit-il être disponible dès que les deux membres sont vivants en rangée avant (comme une option de menu supplémentaire), ou nécessiter une jauge de charge dédiée au binôme (fidèle à Octopath Traveler II) ? Ce choix impacte directement le schéma duoPairs proposé en section 04 (ajout probable d'un champ comboGauge si la seconde option est retenue).
Fichiers concernés : src/core/formulas.ts, src/core/combat.ts, src/core/stats.ts, src/scenes/CombatScene.ts
Phase 3 — Boucle roguelite (rencontres, récompenses, routes)🟡 Moyenne
Objectif : assembler les fondations des Phases 1-2 en une boucle de run jouable.
  • Nouvelle donnée RunNode/nodes.json : graphe de rencontres (combat, combat d'élite, boss, récompense, repos, route).
  • Nouvelle donnée routes.json : événements de recrutement ou d'échange de personnage, condition de déblocage (ex. profondeur de run minimale).
  • Structure de RunState (roster débloqué ce run, formation active, monnaie, nœuds franchis) — état de session, pas nécessairement persistant tant que la sauvegarde n'est pas priorisée.
  • Écran de sélection du personnage de départ (nouvelle scène ou extension de MainMenuScene).
  • Génération simple de rencontres à partir de enemies.json — dépend en parallèle de l'enrichissement du contenu ennemi (actuellement 1 seul ennemi défini), qui reste secondaire par rapport à la Phase 1 mais doit progresser avant que cette phase soit jouable.
Fichiers concernés (nouveaux) : src/data/nodes.json, src/data/routes.json, src/core/run.ts (nouveau), src/scenes/*
Phase 4 — Boss et équilibrage🟢 Différée volontairement
Objectif : une fois le socle Personnages/Classes/Compétences et la boucle roguelite stables, spécialiser le contenu de fin de run.
  • Extension de EnemyTemplate pour les boss : patterns d'attaque multiples, phases de Break spécifiques, éventuellement plusieurs boucliers par élément.
  • Équilibrage global des stats/compétences sur la base des données de jeu accumulées pendant les Phases 1-3.
  • Explicitement hors scope tant que les Phases 1-3 ne sont pas validées, conformément à la priorité donnée par le projet.

04Architecture de données ciblée

Extension du pattern JSON + wrapper TypeScript déjà en place dans src/data/. Les champs marqués NOUVEAU dans les exemples ci-dessous n'existent pas encore dans le dépôt actuel ; tout le reste correspond aux interfaces déjà présentes dans src/core/.

Skill — src/core/skills.ts / src/data/skills.json

interface Skill {
  id: string;
  name: string;
  type: "physical" | "magical" | "support";
  element: DamageType | null;
  power: number;
  spCost: number;
  bpScaling?: "power" | "hits";
  target: "single_enemy" | "single_ally" | "self";
  tags?: DamageType[];
  breakPower: number;              // NOUVEAU — remplace le -1 fixe codé en dur dans formulas.ts
  lpGain?: number;                 // NOUVEAU — remplace le champ "ipGain" documenté mais jamais implémenté
  isBurst?: boolean;               // NOUVEAU — compétence de Pouvoir Latent (consomme lp === maxLP)
  requiredRow?: "front" | "back" | "any";  // NOUVEAU — contrainte de rangée
  isDuoCombo?: boolean;            // NOUVEAU — nécessite un binôme actif en rangée avant
}
