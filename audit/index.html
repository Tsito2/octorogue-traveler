01Résumé

Octorogue Traveler est un prototype technique vertical : une tranche jouable de bout en bout (menu → combat de démonstration) repose sur un moteur de combat au tour par tour déjà relativement riche (dégâts physiques/magiques, critiques, précision/esquive, Break/bouclier, Boost Points, Influence Points). Le dépôt contient cependant deux systèmes de combat parallèles : un module actif et connecté (src/core/ + src/scenes/), et un module orphelin plus ancien (src/characters/, une partie de src/combat/, src/ui/) qui n'est importé par aucun fichier exécuté. Le contenu de jeu reste minimal (2 héros, 1 ennemi, 2 compétences, 1 décor, 1 musique) et plusieurs pans entiers du jeu visé sont absents : exploration, dialogues accessibles, sauvegarde, progression, inventaire.

Point d'attention principal : le module orphelin (characters/, une partie de combat/, ui/) duplique le moteur de combat actif avec une API différente. Aucun fichier de src/index.ts ne l'importe — c'est du code mort qui augmente la dette technique et le risque de confusion.

05Dette technique

  • Code mort : module characters/ + combat/* (hors scènes) + ui/, jamais importé par src/index.ts, duplique le moteur de combat actif.
  • Documentation désynchronisée : README.md racine décrit une arborescence obsolète et référence un asset (menu-bg.png) qui n'existe pas.
  • CI probablement inactive : config.yaml est à la racine du dépôt au lieu de .github/workflows/ ; le script lint qu'il implique n'existe pas dans package.json.
  • Cas spécial hors donnée : l'action "defend" est codée en dur dans CombatEngine.resolveAction plutôt que définie dans skills.json, cassant l'homogénéité du système data-driven.
  • Absence totale de tests alors que formulas.ts/combat.ts contiennent la logique la plus critique (calculs de dégâts, Break) et sont facilement testables unitairement.
  • BP et IP invisibles/inutilisés côté joueur malgré une implémentation moteur complète — écart entre le potentiel du moteur et l'expérience réellement jouable.

08Recommandations

Avant d'ajouter du contenu : trancher le sort du module orphelin et mettre à jour le README.md. Ces deux actions sont peu coûteuses et lèvent l'essentiel de la confusion architecturale actuelle.
Avant d'enrichir le combat : fermer les boucles existantes (ciblage joueur, dépense de BP visible, suite après victoire/défaite) plutôt que d'ajouter de nouvelles mécaniques (statuts, IP) sur des fondations encore incomplètes.
Pour sécuriser la suite : ajouter des tests unitaires sur formulas.ts et combat.ts avant d'enrichir significativement le contenu (plus de compétences/ennemis augmente rapidement les combinaisons à vérifier manuellement).
